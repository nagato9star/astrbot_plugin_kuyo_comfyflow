# Anima：提示词组装与工具调用

## 当前插件里的工作方式

适用场景是 AstrBot 在日常聊天中通过 Kuyo ComfyFlow 生图。保留当前人格、称呼和对话；提示词编写是完成用户画图需求的一部分。

### 工具怎么选

| 用户要做什么 | 当前入口 |
|---|---|
| 用文字自由画新图、选择风格和 LoRA | `comfyui_draw`，填写实际可用的 `model_family` 和 `prompt` |
| 复用已有画风或设置 | 需要时用 `comfyui_lookup(type="recipe")` 看用途，再用 `comfyui_recipe_draw` |
| 修改附图或已有图片 | 使用已配置的 `comfyui_edit` 路由 |
| 查角色、画师或兼容资源 | `comfyui_lookup`；已确认的资源不用为走流程再查一遍 |
| 用户询问进度、取消或取回结果 | `comfyui_job`，按本次任务操作 |

家族名、配方名、文件名及可选参数以运行时工具为准。原教程配套的 API 生图脚本、标签管理器和 prompt 仓库未接入本插件，不调用它们，也不另造一条提交链。

### 风格可以主动选择

用户给了目标画风，就据此选择已有配方，或搭配兼容的 LoRA 与画师。现成方案合适时直接复用；要自由换资源时使用 `comfyui_draw`。不用限制成一个主 LoRA 或一主一辅，也不为了增加变化而盲目叠加。

优先沿用已选底模和当前服务端；明确换底模、改工作流或跨服务端时按用户要求处理。配方、模型文件和参数从当前安装的实时目录与工作流中获取，不假定存在特定用户的组合。

### 排队之后怎么接话

工具回包表示已入队时，按当前人格简短回应并继续聊天。完成后由插件发图，再触发带原请求与历史的回复；此时结合用户具体要画的内容自然接话。

生成、保存和送达分别以实际结果为准。无需照读任务编号、固定报数量、反复轮询或重新发送已经交付的图片。用户明确要看提示词时再展示提示词，日常生图不必把完整参数当聊天回复贴出来。

## 提示词与工具字段

原教程的“一行 prompt”用于它自己的脚本接口。在插件中，把画面描述填入工具参数；正常聊天仍沿用当前人格与回复处理流程。

### 按现有槽位分工

| 内容 | 插件中的处理 |
|---|---|
| 本次主体、动作、外观、构图和场景 | `prompt` |
| 原生画师或需要覆盖的媒介风格 | 工作流有对应映射时用 `artist` |
| 本次确需补充的质量词 | 有对应映射且需要调整时用 `quality`；通常沿用模板 |
| 本次新增排除项 | 用 `negative`；实际合并方式取决于槽位 |
| 已选 LoRA 的可信触发词 | 有独立映射时用 `trigger_words`；按原样填写 |
| 可选风格 LoRA | `lora` 对象数组，权重放在 `strength` |

当前代码只写已映射的文本字段，不会自动把缺少映射的 `artist`、`quality` 或 `trigger_words` 拼回主提示词。已知模板没有独立字段时，把必要的画面风格或触发词组织进它实际读取的 `prompt`，避免漏写；有独立字段时也不重复拼两遍。

### 哪些沿用，哪些覆盖

自由生图省略可选参数会沿用家族工作流；配方生图继承该配方保存的设置。`comfyui_recipe_draw` 当前只公开本次 `prompt`、配方名、方向和种子；需要换 LoRA、底模或采样时切到 `comfyui_draw`，不要给配方工具编造覆盖参数。

`lora=[]` 用于关闭映射中的可选 LoRA；独立的固定加速 LoRA 保留。`trigger_words=""` 可以显式清掉旧触发词；其他文本字段不能一概假定传空字符串就能清空模板。追加模式的负向词也不能靠传空撤回。

### 文本怎么写

遵循当前家族的 `prompt_style`。tag、自然语言及混合写法都可按任务使用：tag 控制直观特征，短句说明归属、交互与空间关系。普通 tag 的写法与自然语言专名分开处理，LoRA 专用 token 保持元数据原样。

原生画师保留 `@` 前缀；用户点名或已有可靠拼写时直接使用，不确定时查询。质量词和画师是否已经固定由当前工作流决定，不能直接继承原教程“脚本已处理，全部禁止”的前提。

光源、阴影与色调可服务于用户要求。只有实际使用的光效方案存在明确约束时才避让，不把它扩大成所有 Anima 图的禁令。提示词加权依赖当前编码流程，不把 LoRA 的数值权重写成主提示词正文。

本地两段采样可能使用不同模型、LoRA、CFG、采样器和种子；默认沿用配方或已确认映射，不为了套教程统一两段参数。

## 按当前需求组织和检查

### 组织画面

可以先确定主体与身份，再补外观、服装、动作、表情、镜头、环境和媒介。这个顺序帮助检查遗漏；重要关系已经表达清楚时，不必为满足固定槽位表重新排列全文。

细节数量由画面需要决定。简单头像保持简洁，带环境的插画写清人物在做什么、接触什么物件，以及人物和背景的位置关系。无需为了达到 16、30 或 48 个标签而补内容。

视线跟随动作和构图：读书看书、交谈看对方、背影望远处都自然。没有明确理由时不自动注入直视镜头；只有需要观众互动的画面才补人物与观众的关系。

多人时，将各自的位置、身份、外观和服装放在相邻描述里，再说明彼此动作。角色名不够明确时补有依据的辨识特征，不硬凑固定数量的外观锚点。

### 冲突要结合画面判断

检查同一角色、同一镜头、同一时刻的要求是否能同时成立。不同角色、分镜、镜面或局部特写可以各自采用不同状态，不能把整组词脱离主体当作固定互斥表。

用户刻意要求传统服饰与未来城市同框，就保留这种混搭；用户要求纯色、留白或极简背景，也照要求写。风格一致性用于完成目标，不用于替用户改题材。

### 提交前做一次实际核对

- 人数、身份、服装版本和核心动作与请求一致，附加特征没有覆盖用户指定内容。
- 手、道具、视线与支撑关系说得通；重复或互相抵消的表达已清理。
- 资源与家族兼容，所需触发词进入实际读取的字段；模板已有质量和负向设置得到保留。
- 构图、画幅和文字要求与本次目标一致；修改参数只针对用户想改变的部分。

核对在内部完成，不把勾选表、标签统计或推理过程发给用户。提交后只根据实际回包说明状态；没有读取成图，就不声称脸、手、文字或画面效果已经通过检查。

需要细节词汇时再回 [资料目录](../index.md) 选择外貌、服装、镜头或环境章节。原文的固定字数、强制视线和作者脚本约束以本场景说明为准。
